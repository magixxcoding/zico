How to build a CDN, one edge at a time.

A practical tour through caching, edge locations, and the small decisions that make the web feel fast.

By M2HBOctober 8, 20268 min read

A page can be beautifully designed, carefully written, and still feel slow if every request has to travel halfway around the world. A content delivery network (CDN) tackles that distance problem by keeping copies of content near the people who need it.

Start with the distance

When a browser asks an origin server for a file, the request and response cross networks that introduce latency. The farther apart the visitor and server are, the longer that round trip can take. A CDN places servers—often called points of presence or edge locations—in multiple regions so commonly requested files can be served from a nearby location.

The simplest version is a cache. On a cache miss, an edge server fetches an asset from the origin, stores it according to its caching rules, and returns it to the visitor. The next matching request can be answered locally. For static files such as images, stylesheets, and scripts, this can dramatically reduce repeated trips to the origin.

Decide what can be cached

Caching is a promise: for some period of time, the stored response is good enough to reuse. Versioned assets—like app.a81c2.js—are good candidates for long lifetimes because changing the content also changes the URL. HTML and personalized responses need more care. Cache-control headers should describe whether a response is public, private, immediately stale, or safe to reuse for a defined period.

A cache is only as useful as its invalidation story. Make stale content predictable before you make it fast.

When content changes, a system needs a way to refresh it. Short time-to-live values are easy to operate but may briefly serve old content. Purging provides more control but adds complexity. A common, robust approach is to use content-hashed filenames for static assets and conservative freshness rules for pages that can change independently.

Route requests, measure results

DNS and routing direct visitors toward an available edge. From there, the CDN may serve a cached response, fetch from the origin, or proxy a request that should not be cached. Availability matters too: health checks, regional failover, and sensible timeouts keep one unhealthy location from becoming a site-wide problem.

Measure cache-hit ratio alongside user-facing latency, error rate, and origin load. A high hit ratio is not automatically a good experience if important pages are slow or stale. Start with a small set of cacheable files, inspect real traffic, and adjust based on evidence.

Build the smallest useful version

A CDN is not one magic server but a set of clear policies: where requests go, which responses can be reused, and how the origin is protected when an edge cannot help. Get those fundamentals right first. More advanced features—image transforms, edge logic, and request shielding—can follow when a real need appears.

The web feels fast when distance stops being the visitor’s problem. A thoughtful cache is one of the simplest ways to make that happen.
